# Wanted invitations and local requester policy

Offerer binds an explicitly installed prospective provider Registry, local
identity, Peer Protocol/Services authorities, finite limits and read-only Gate.
offer requires outgoing Request permission, Services Invoke permission and a
current retrieved wanted Selection whose publisher is the opposite endpoint.
The exact provider implementation must exist before emitting offer. A remote
schema or installation suggestion cannot install one. Offered retains exact offer
bytes, original association, selected terms, local deadline and opaque owner scope.
proposal consumes only that original invitation on the same authenticated stream
and uses Authorizer to validate the publisher's locally chosen proposal. It still
does not reserve, execute or compel the publisher to spend.

On the publisher, request requires separate incoming Invoke, local Request and
Services Request grants through PublisherContexts, plus authoritative current
wanted terms. It checks the invitation's ID/service/version and explicit roles
before invoking trusted Policy.choose. The policy receives only selected contract
and authenticated prospective provider and returns locally owned input and
Spending as Work, or refuses. Terms are rechecked after that callback. Client then
independently validates input/terms and encodes propose. Unknown optional input or
installation hints are inert and never become application authority.

The publisher is requester while the stream opener is provider. Original operation
keys still name the requester. Subsequent quote, exact consent, two-sided holds,
input/result terminal gates and settlement use the same contracts as provided work.
No invitation authorizes spending, quote acceptance or provider execution. Missing
provider support, wrong roles/stream/owner, deadline failure and policy refusal
produce no proposal or charge. Composition must enforce the wanted offer/propose
sequence through Exchange before dispatching these narrower semantic helpers.
